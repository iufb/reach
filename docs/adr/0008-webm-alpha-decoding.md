# 0008. Видеостикеры: свой разбор WebM и два MediaCodec для цвета и альфы

- Статус: принято
- Дата: 2026-11-20

## Контекст

Видеостикеры и часть кастомных эмодзи (PRODUCT.md §4.4, §4.5, #175, #176) — это WebM с VP9 и прозрачностью. Альфа в WebM лежит не в основном потоке: libvpx/ffmpeg кодируют её отдельным VP9-кадром той же длины и кладут в Matroska `BlockAdditional` (`BlockAddID` = 1), яркость этого кадра — прозрачность.

Media3/ExoPlayer и `MediaCodec` эти данные не читают: стикер проигрывается на чёрном фоне. Варианты:

1. libvpx через media3 `decoder-vp9` — на Maven не публикуется, собирать из исходников с NDK в CI; альфу он тоже не выводит, пришлось бы дописывать.
2. ffmpeg (как в официальном клиенте) — свой JNI, сборка в CI, +несколько МБ к APK.
3. Свой разбор WebM и два штатных декодера: один для цвета, второй для альфа-кадров; ARGB собирается на CPU.

## Решение

Вариант 3.

- `media/webm/WebmParser` — минимальный разбор EBML: первая видеодорожка VP8/VP9, кадры (`SimpleBlock` и `BlockGroup` с `BlockAdditional`) целиком в память. Файлы маленькие (≤ 256 КБ, ≤ 3 с).
- `media/webm/WebmDecoder` — два `MediaCodec` в синхронном режиме, выход YUV 4:2:0 в `Image`, сборка ARGB (BT.601/709, ограниченный/полный диапазон из формата выхода), круг через `flush`. Предпочитаем программный декодер: аппаратные экземпляры наперечёт и нужны обычному видео.
- `media/VideoStickers` — кэш разобранных файлов, не больше 8 играющих одновременно, отдельные потоки для декодирования; `VideoStickerImage` рисует кадр на `Canvas` с тройной буферизацией и прореживает кадр, если он заметно больше места на экране.

## Последствия

- Нет новых зависимостей и нативного кода; APK не растёт.
- Сборка ARGB на CPU: ~512×512 на кадр. Для ленты стикеров хватает; если на кастомных эмодзи в длинных текстах станет тяжело — вынести сборку в шейдер (два `SurfaceTexture` → GL) или перейти на ffmpeg. Интерфейс `VideoStickerImage` при этом не меняется.
- Лейсинг и неизвестный размер вложенных элементов не поддержаны: в стикерах Telegram их нет.
