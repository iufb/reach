# 0013. TGS через rlottie и кеш кадров

- Статус: принято
- Дата: 2026-11-24

## Контекст

Анимированные стикеры, эмодзи и реакции (TGS — Lottie JSON в gzip) рисовал `lottie-compose`, программно на UI-потоке. На средних телефонах (Redmi Note 10S) чат с 3–4 стикерами — 20–26 мс на кадр, половина кадров с рывком (#289, #304, #315). Варианты: rlottie, кеш кадров поверх Lottie, или оба. Владелец выбрал оба — как в официальном клиенте.

## Решение

- **rlottie** (Samsung, C++) и **lz4** статически в `librlottiejni.so` с тонким JNI-мостом (`native/rlottie`). Версии зафиксированы коммитами в `.github/workflows/rlottie.yml`.
- Сборка — как у TDLib (ADR-0001, ADR-0002): отдельный workflow собирает `.so` под `arm64-v8a` и `x86_64` (NDK r28, страницы 16 КБ) и публикует `rlottie.zip` как GitHub Release. Модуль `core:rlottie` скачивает его Gradle-таском по тегу `rlottie.release` из `gradle.properties` и даёт Kotlin-обёртку `RLottie`. Бинари в git не коммитим.
- `media/Tgs.kt`: `TgsImage` рисует кадры в фоновых потоках (3 потока) в тройной буфер, UI только выводит готовый битмап. Размер кадра — по месту на экране (не больше 720 px), петли стикеров — 30 fps, разовые анимации — 60 fps.
- **Кеш кадров**: отрисованный круг (размер + шаг кадров) сжимается LZ4 и кладётся в LRU на 48 МБ сжатого; следующие круги и повторные показы только распаковывают. Круг больше четверти кеша не кешируется — рисуется заново. Первый кадр из кеша показывается сразу в композиции, без заглушки.

## Последствия

- Меняете JNI-мост или версии — поднять `JNI_VERSION` / коммиты в workflow, дождаться релиза и обновить `rlottie.release`.
- +~0,6 МБ нативного кода на ABI; `lottie-compose` убран.
- Отрисовка не на UI-потоке, но CPU тратится: на слабых телефонах при отставании кадры пропускаются, а не догоняются.
